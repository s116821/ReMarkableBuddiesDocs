# Conversation management companion

## Purpose

Provide explicit ordinary historical-conversation logical removal and original-only reconciliation in both Manager companions. Independent source review and Windows/Linux retained-package qualification are accepted. The [archived detailed contract](../../changes/archive/2026-10-28-manage-historical-conversation-companion/contract.md) defines exact wires and lifetime limits; its [results](../../changes/archive/2026-10-28-manage-historical-conversation-companion/results.md) preserve exact qualification and original failures. The [public guide](../../../docs/manager-conversation-management.md) links the reviewed Manager manual. Physical tablet/native/runtime health and official release are not established; final paired review, normal merge and actual-main/publication verification remain separate gates.

## Requirements

### Requirement: Explicit fresh ordinary conversation preview and confirmation
Both Manager companions SHALL offer a separate initially unselected management flow over the unchanged supported ordinary historical-conversation producer. Selection SHALL come from a complete current identity-matched candidate snapshot. The host SHALL require fresh Inspect then fresh Prepare before a deliberate once-only Confirm, bind each stage to one host-issued reference and original target, and publish only bounded counts and safe outcome fields.

#### Scenario: Discovery does not grant deletion authority
- **WHEN** a completed inventory lists a conversation UUID
- **THEN** the user must explicitly select it and obtain a fresh selected-target Inspect and fresh Prepare; neither the list nor the inspect counts authorize Confirm.

#### Scenario: Preparation observes changed eligibility
- **WHEN** a conversation changes between Inspect and Prepare
- **THEN** the fresh producer result replaces the old preview or refuses; no cached counts, empty fallback, repair or implicit retry authorizes removal.

#### Scenario: Preview expires or is invalidated
- **WHEN** a peer operation, selection/identity change or120000ms stage expiry invalidates a preview
- **THEN** its reference cannot Confirm and no automatic new operation is created.

### Requirement: Original-only reconciliation distinguishes acknowledgment and current state
The host SHALL retain exact private original bytes before possible Apply dispatch, issue at most one Apply for that reference and permit only bounded explicit read-only Status afterward. Historical acknowledgment SHALL remain distinct from current root/binding state, and uncertainty/refusal SHALL never authorize another Apply or replacement preparation.

#### Scenario: Apply reply is lost
- **WHEN** Apply may have dispatched and its reply is lost, malformed or stale
- **THEN** the original reference remains unknown and offers only Status using identical original intent bytes under the same connection/boot and original nonrenewable expiry.

#### Scenario: Original receipt survives later changes
- **WHEN** Status acknowledges the exact original receipt with current_state changed
- **THEN** the UI shows historical acknowledgment and changed current state separately without another write or restoration claim.

#### Scenario: No exact original receipt is proven
- **WHEN** Status returns unchanged or unresolved, including tombstones or partial original objects without a complete receipt
- **THEN** the UI preserves that exact observation and never claims historical no-deletion, acknowledged removal, retry permission or physical reclamation.

#### Scenario: Recovery custody is exhausted
- **WHEN** original bytes expire, the bounded ledger/capacity is exhausted or the host process restarts
- **THEN** Status is unavailable without eviction, expiry renewal, persisted token import or a substitute fresh operation.

### Requirement: Strict private wire and safe parity
Both actual host adapters SHALL use the fixed existing conversation-maintenance CLI under current wired identity checks, strict bounded JSON/intent/report/receipt admission and safe public reduction. The twelfth owner SHALL preserve all predecessor exclusion/original semantics, local observation quiescence, exact per-invocation cancellation and sandboxed browser/Electron/manual parity.

#### Scenario: Untrusted output cannot become a safe empty result
- **WHEN** output has an invalid frame, version, digest, receipt, selector/status combination or identity
- **THEN** static safe refusal or retained original uncertainty is returned with no raw fields, content, paths or diagnostic leak and no alternate command.

#### Scenario: A peer owns maintenance I/O
- **WHEN** another bounded maintenance owner holds the real shared token
- **THEN** management returns Busy before hooks, invalidation, timers, cancellation or helper launch and preserves every original operation.

#### Scenario: Delayed cancellation races a newer original check
- **WHEN** an old invocation's cancellation arrives after another Status began for the same reference
- **THEN** it cannot cancel or release that newer invocation's child, deadline or token.

#### Scenario: Stop while observation is queued
- **WHEN** the user stops or the renderer wait expires during observation quiescence
- **THEN** that continuation never dispatches later, clears idle views and preserves original uncertainty without using global cancellation as a pause mechanism.

#### Scenario: Logical removal is acknowledged
- **WHEN** the producer verifies the original logical-removal receipt
- **THEN** the UI explains that retained history/media/export associations/native pages remain, runtime is unverified, and no physical-space or synchronized-delete claim is made.
