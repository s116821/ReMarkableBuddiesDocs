# Prepared one-fact memory forget in both companions

## Purpose

Provide explicit conditional forget using one private live-host intent and a
separate historical receipt workflow in the browser/helper and Electron app.

## Requirements

### Requirement: Separate deliberate supported-value preparation
Both companions SHALL prepare a new supported single-value preview for an explicitly
selected inspected global key before any forget confirmation. Read-only search or
detail SHALL NOT grant mutation permission; exact preview, verified target and
local/selected group effect SHALL be shown for deliberate confirmation.

#### Scenario: Confirm a separate fresh preview
- **WHEN** the user explicitly prepares a displayed supported fact
- **THEN** both hosts obtain and validate a new same-admission producer preview, show its exact fact/target/scope and require a separate explicit confirmation.

#### Scenario: Nonconfirmable state
- **WHEN** preparation sees absent, tombstone, competing, opaque, invalid or unsupported numeric data
- **THEN** no executable preview is offered and no head is selected or filtered to manufacture permission.

### Requirement: Immutable single live-host intent custody
One bounded private slot per live host SHALL reserve preparation before awaited
I/O and bind an opaque public reference to immutable original bytes, preview digest
and original target/boot/host-session epoch. Competing tabs SHALL NOT replace its
target; public callers SHALL NOT provide private intent, heads, paths or pins.

#### Scenario: Competing tab preparation
- **WHEN** another tab prepares while a nonterminal original intent occupies the shared helper
- **THEN** it receives Busy/refusal without replacing the first tab's record or confirmation target.

#### Scenario: Foreign or stale public reference
- **WHEN** a caller submits an unknown, expired, replaced or wrong-session reference or extra private fields
- **THEN** host guards refuse before dispatch and never substitute another retained intent.

### Requirement: Single-use conditional confirmation
The host SHALL atomically claim the original prepared reference before possible
confirmation dispatch and SHALL never rearm it or generate a replacement intent on
failure. Exact producer binding/content/currentness and atomic publication remain
producer authority, not client inference from mode or head IDs.

#### Scenario: Duplicate confirmation
- **WHEN** two same-host confirmations race for the same ready reference
- **THEN** at most one sends the fixed original CLI input and the other refuses without another mutation attempt.

#### Scenario: Lost or cancelled reply
- **WHEN** confirmation may have dispatched and no complete exact matching successful report arrives
- **THEN** the host clears stale detail and retains original bytes/unknown outcome without retry, optimistic removal or replacement UUID/heads/mode.

### Requirement: Historical receipt and honest lifetime limits
Receipt reconciliation SHALL be separate, explicit and read-only using retained
original bytes and provable original bindings. Historical acknowledgement SHALL
NOT claim current deletion. Refresh/disconnect SHALL preserve possible-dispatch
uncertainty in the live host; full restart custody loss SHALL never imply no commit.

#### Scenario: Receipt after later value
- **WHEN** the exact original operation has a provable historical acknowledgement while current data later changed
- **THEN** the UI shows historical acknowledgement only and requires a fresh deliberate inspection for current heads, with no extra tombstone.

#### Scenario: Receipt absent or binding drifted
- **WHEN** receipt proof is absent, unavailable or no longer admissible
- **THEN** outcome remains unresolved and receipt never falls through to confirmation or makes a not-dispatched claim.

#### Scenario: Refresh and full host restart
- **WHEN** a renderer refreshes/disconnects or the complete host loses its private slot
- **THEN** ready confirmation is invalidated, retained live-host uncertainty remains visible where state survives, lost custody is unavailable/unresolved and no automatic new intent is created.

### Requirement: Exact bounded private protocol and public projection
The host SHALL use only fixed prepare/forget/receipt stdin selectors with exact
original input, truthful phase/status/incomplete/outcome framing and strict smaller
caps. Preview content hash SHALL follow the producer canonical-byte recipe. Both
public bridges and controller SHALL validate reduced views without private authority.

#### Scenario: Wrong phase or unsafe content
- **WHEN** a report mismatches selector/operation/outcome, canonical preview hash or supported numeric/schema shape
- **THEN** the whole response refuses; after possible dispatch uncertainty remains and raw private content is never exposed.

#### Scenario: Invalid or partial transport
- **WHEN** UTF8/duplicates/size/EOF/exit/deadline/single-report validation fails
- **THEN** no partial preview, acknowledgement, empty success or automatic repeat is produced.

### Requirement: Paired evidence and delivery boundaries
Implementation acceptance SHALL use attributed actual producer cases and both
protected browser/Electron paths with ordinary retained-package checks, preserving
synthetic fault attribution, source ownership and full own OpenSpec lifecycle.

#### Scenario: Qualified consumer delivery
- **WHEN** the paired increment is proposed for normal delivery
- **THEN** actual producer bytes verify compatibility and required host/package controls pass without claiming physical tablet/provider/service qualification or durable recovery.

#### Scenario: Prior delivered inspection
- **WHEN** this new workflow is implemented
- **THEN** prior inspection/search semantics and unrelated producer/SDK/release source remain preserved and no read success is reinterpreted as write authority.

Source basis: coordinated Manager implementation and accepted producer contract;
see the paired archived verification for exact revisions, actual producer bytes,
synthetic host faults and retained-package qualification. Native and broader
management gates remain separate.
