# Design

## Current behavior and ownership
Delivered local corrections retain explicit confirmed sample/text pairs under Handwriting1. Reader's existing two-pass analysis and Writer generation do not consume them. The shared LLMEngine supports text/image parts and progress callbacks with joined cancellation. The configured OpenAI-compatible transport bounds a response to10 MiB and4000 completion tokens. Reuse it; do not add a worker, dependency, model installation or new persistence format.

## Proposed operation
A new handwriting_transcription command module owns admission, exact context capture and a held report. Extend the existing retrieval::notebook normalizer through normalize_with_confirmed_context; reuse its strict PNG container checks, image decoding, ordered page reply parser, source identity and production progress path. Do not add a parallel OCR parser. Existing normalize remains an exact no-context wrapper with unchanged serialized results, prompt bytes and identities. Its public typed run function accepts an already selected engine and progress callback so both applications can later reuse it. The CLI resolves effective provider configuration only after input/context admission and before invocation. It does not start the device, native workflow or a sync worker. REMARKABLE_BUDDIES_CONFIG selects the config exactly as for the existing handwriting command.

The target is one explicitly supplied historical page with asserted nonnil document UUID and positive page number. The request selects exact examples, not an implicit profile-wide search. Null context means no Store is opened. Non-null context requires a profile and one to three distinct correction/revision pairs in caller order. Open the existing Store once, retain ordinary/local-domain ownership and validate selected-mode and legacy-publisher exclusion before reading. Capture at most4096 envelopes/8 MiB once, restricted to the requested profile/keys. Reuse the correction provider's lineage/identity/media rules through typed shared helpers, not a second permissive decoder or JSON report round-trip. Each selected correction must have exactly one active supported value head equal to the requested revision and an available verified original PNG. Any stale/conflicted/tombstoned/unknown/incomplete example refuses the entire context before calling the engine. No fallback to no-context, historical heads or another profile. Record these as captured facts, not a promise they remain current after the report is released.

## Resource and output bounds
Target admission reuses the existing notebook PNG container/decoder, lowered to one page: at most8 MiB compressed, dimensions1..4096 and at most8,000,000 decoded pixels with64 MiB allocation cap. Each retained example keeps the delivered correction bounds512 KiB, dimensions1..2048,4,194,304 pixels. Input cap12 MiB plus one rejection byte, one target only; examples are references, never paths. At most three examples plus target means at most9.5 MiB compressed images and20,582,912 pixels, decoded sequentially. No resize, crop, recompression or sample substitution is performed for admission. Original/corrected example texts are individually at most4096 UTF-8 bytes, retained identity descriptions are not sent. Prompt text excluding images is at most32 KiB after JSON serialization and complete serialized prompt descriptor at most24 MiB, matching the existing maximum. Refuse rather than truncate. Use lowered Options for the one target: model reply at most16 KiB before the existing strict pages parser, target transcription at most4096 UTF-8 bytes, normalized result and complete emitted report each at most32 KiB (the report includes its final newline). Three confirmed examples are context, never counted as target pages or emitted as source units. Existing HTTP response cap remains10 MiB; this module does not claim that its smaller parsed-text cap bounds the complete HTTP wire response.

## Data and prompt separation
Retain the existing fixed notebook INSTRUCTIONS and its strict pages reply. With selected examples append the exact context instruction in prompt-v1.txt: use examples solely as possible reading references; transcribe only the subsequent target historical page. Append a JSON descriptor for each example immediately before its image, then the unchanged target page manifest/descriptor/image last. Descriptor is a compact JSON map with sorted keys corrected_text,index,kind,original_text, with kind=confirmed-example and one-based index. Other prompt-part/map keys retain the existing sorted-key json! serialization. Full ordered descriptor parts and typed Profile bytes are frozen in identity-vectors.json. The context instruction is sent with its exact bytes with no trailing newline; target contains no unverified expected answer. Caller cannot supply a system prompt, arbitrary instruction or model parameters. A typed context owns only validated retained examples and cannot be constructed from arbitrary unchecked caller text. Context source links are caller assertions; exact sample hashes and captured revision provenance do not prove native ownership. LLMEngine has no tool capability. Delimiters and fixed ordering reduce accidental instruction mixing; they do not prove adversarial prompt-injection immunity or transcription accuracy.

## Identity and backward compatibility
The existing no-context normalize call stays byte-identical in prompt construction, source image-set digest, Profile protocol1/prompt_revision, extractor revision and NotebookText serialization. Exact serialized field order is Profile(protocol,prompt_revision,caller_model_profile,confirmed_context); confirmed_context(profile,examples); each example(correction,record,revision,sample_sha256,original_text_sha256,corrected_text_sha256). All text hashes use exact UTF-8; sample hashes use exact retained PNG bytes. The nullable field is omitted entirely on old no-context serialization. New with-context results use Profile protocol2, prompt_revision=transcribe-confirmed-examples-v1 and an added confirmed_context field containing profile plus ordered correction/record/revision/sample/text digest descriptors, never image or text content. The extractor prefix is notebook-ocr-confirmed-v1: plus SHA256 of that exact compact serialized Profile; it cannot collide semantically with the no-context namespace. Target source_sha256 retains the existing page-image-set-v1 recipe and includes only the target pages, not examples. Existing prompt_sha256 covers every serialized prompt part including examples and target in order. response_sha256 covers the exact model reply. Context changes affect extractor identity even if corrected text happens to produce the same transcription. No Source3/Conversation3 allocation or source cache install occurs. Freeze literal Unicode/order/context hash vectors and independently verify them before implementation acceptance.

## Calls, cancellation and uncertainty
Check progress before context work, after capture, before adding content, immediately before invocation and after return. The existing engine progress callback remains active during the request; cancellation joins its owned transport work. Exactly one execute_with_progress invocation is permitted per command, no automatic retry/fallback. Repeated explicit invocations, including the same caller invocation UUID, are new calls: no durable request/response receipt or idempotency promise exists. Mark provider_attempt=called immediately before entering that method, meaning invocation was attempted, not proof of HTTP transmission/acceptance. Failures/cancellation once called leave remote outcome unknown; no rollback or learned state is claimed. No Store staging/commit occurs anywhere.

## Lifetime and privacy
The actual LocalCorrections/mode ownership stays inside the held transcription report through write_to success, error or drop, as in the delivered correction provider. Failure paths must not leak the guard. With null context there is no Store lease. The explicit report may contain the proposed transcription; routine logs/errors expose fixed codes/counts only. No target/example image, text, request body, private path or credential is logged. stdout failure does not trigger another report, call or mutation.

## Typed normalization outcomes
The internal normalizer exposes a typed outcome/error boundary for the new caller; the old normalize API preserves its Result<NotebookText> behavior by mapping typed failures without changing default output. Existing model reply status blank produces one empty target unit and blank_pages=[page]. unreadable returns the new command's explicit unreadable status with result=null, never a successful empty document. Other malformed replies use invalid-response. No text is accepted from an unreadable page or JSON with duplicate/unknown/mismatched page entries. Model output is unverified even after schema admission; a valid JSON answer masquerading as text is not semantically detected by schema alone.

## Evidence and integration limits
Actual Store tests must cover exact-revision capture, profile isolation, conflict/tombstone/orphan/missing/corrupt media refusal, publisher exclusion through provider and failed output, and no commit. Capturing fake engines exercise the extended existing normalizer and ordered production payload, not a second transcription implementation. Assert the old normalize path is unchanged with a frozen no-context prompt/profile/source/output vector; the new context path must emit no example as a target unit. Actual CLI subprocesses cover exclusive flags and refusal before Store/provider startup. Cancellation uses the real progress path and an engine that observes its callback; transport joining remains covered by existing transport controls unless changed.

Live evidence is a separate required delivery gate: select new representative retained fixtures for connected cursive, shorthand/technical operators, ambiguous/absent writing and unrelated/misleading examples; establish independent ground truth and exact expected refusal/facts before calls. Compare no-context and selected-context conditions on identical target bytes, bound at most eight calls total with90s timeout each. Preserve every outcome, including degradation; no easier replacement, repeated success fishing, training claim or reuse of old closed experiment as current qualification. Publish only shareable fixture material. If representative fixtures or live access are unavailable, leave the gate open and do not merge. Full Reader/Writer integration, performance, real pen input and efficacy beyond those bounded cases remain later scope.
