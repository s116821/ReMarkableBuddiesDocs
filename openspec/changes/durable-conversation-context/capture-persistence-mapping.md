# Historical SDK capture persistence mapping (proposed)

This consumer mapping follows accepted Docs fbb2fd4 and SDK evidence-facts contract9b61d72, implemented and independently reviewed at644811c and integrated unchanged at SDK7e8ffd51f27cc63d79475754071b6444eab048fb. Buddy pins that exact SDK source revision at build time; this is experimental consumption, not a licensed/public SDK release or native qualification.

Buddy will use a separate typed historical capture payload over the existing Store, linking its conversation/turn and capture operation without implementing a second native journal. It preserves the entire SDK-owned facts shape through read-only accessors: observation and ordered identities; receipt/capture roles where applicable; original intervals and synthetic clock/qualification/render labels; parent/derivative descriptors, scope, lineage, target and geometry. SDK owns field meaning and schema. Buddy's storage container uses canonical UUIDs and explicit named enums, u64 values and geometry bits encoded as canonical decimal strings, and Duration seconds/nanoseconds components. Unknown fields/versions/names and missing required facts refuse domain use; high integers never pass through floating-point JSON numbers. Captured bytes are stored as existing content-addressed media with exact hash/length/MIME. A parent is retained even when not submitted to a provider. Facts do not contain a live guard and cannot be converted into one.

Current SourceObservation/ImageUse convenience projections are incomplete for SDK facts. The integration must avoid filling their native-profile or global-clock fields with invented placeholders. Missing native capability/profile and absolute capture time remain explicitly absent for synthetic acquisitions; complete historical SDK facts are authoritative for inspection. Synthetic fixture preparation may be exercised through a clearly labelled model path, while any consumer operation requiring native qualification refuses UnqualifiedSyntheticModel. Existing handwritten synthetic domain fixtures remain labelled and are not retroactively promoted to native evidence.

Before actual Reader integration, commit the prepared turn, linked complete capture facts and all parent/provider media atomically using full root heads. Retried preparation returns stored bytes and historical acknowledgment without recapturing. The provider-facing batch contains every originally submitted derivative in its original order; the native parent is separately retrievable. A missing/corrupt required record or media refuses image-dependent dispatch. Text inspection may expose explicitly unavailable evidence, but cannot present a silently incomplete history as complete.

Verification must persist to the real Store, drop/reopen it, inspect every original field and bit pattern, and retrieve exact media bytes. Cover multiple devices/adapter instances with identical PageKeys, values above2^53/u64::MAX, signed-zero geometry, absent native profile, unknown SDK schema/names, tampered fields, byte/object failures and refusal to restore a live guard. A recording-provider fixture must observe exact retrieved proposal/verification bytes; this is distinct from actual Reader orchestration and qualified tablet evidence. Complete consumer DTO/reopen acceptance does not complete REM37, SDK native acquisition, canonical sync/archive or ecosystem release gates.
