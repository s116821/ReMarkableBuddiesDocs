## MODIFIED Requirements

### Requirement: Explicit selected Reader startup and historical handling

An explicitly configured selected Reader runtime SHALL preserve the refusing
default unless current SharedGroup document readiness, current effective
Reader enablement and the existing installed resident source and health
owners admit the Reader input route. It SHALL establish effective enablement
before quiet startup activation and independently at each genuine release
before request admission, activation or capture. The exact released-request
policy and mode pins SHALL remain fixed through capture, Prepare and all model
and result stages. Absent, stale, Joining or disabled policy SHALL refuse
before new native activation, capture or model credential access. The route
SHALL preserve ordinary LocalOnly routing, existing-only Store custody and
independent historical handling without legacy downgrade.

Without admitted installed input, explicit selected startup SHALL resolve
unsupported committed SDK acquisition before model credentials, provider, sync
or native device startup. One-shot historical inspection and recovery SHALL
retain immutable provenance and grant no live context or effect authority.

#### Scenario: Qualified resident input without output

- **WHEN** an installed source and supervised health owner admit a genuine
  Reader release for the exact registered document
- **THEN** the same selected Store receives one bounded historical capture
  and one fresh Prepared acknowledgment through the selected route, without
  ordinary acquisition or native output authority.

#### Scenario: Shared disable overrides the local Reader flag

- **WHEN** saved Reader is enabled and the admitted current shared declaration
  disables it
- **THEN** selected startup and the released-request boundary refuse before
  activation, capture, Prepared publication or model credentials.

#### Scenario: Shared enable overrides the local Reader flag

- **WHEN** saved Reader is disabled and the admitted current shared declaration
  enables it
- **THEN** the effective policy allows the existing selected input route to
  proceed through its remaining installed and currentness checks.

#### Scenario: Idle startup authority changes before the first release

- **WHEN** effective Reader or SharedGroup custody changes between idle startup
  and the first genuine release
- **THEN** the release is independently checked against current policy and mode
  custody. An unavailable, stale or disabled request performs no new
  activation or capture and resolves no model credentials. A changed preference
  that remains enabled under the same admitted mode can proceed only with its
  newly admitted pins, frozen within the original release deadline.

#### Scenario: SDK native acquisition remains unsupported
- **WHEN** explicit selected startup uses the committed unqualified SDK platform
- **THEN** it SHALL report the typed unsupported capability without constructing ordinary RealDevice, invoking a model, publishing a pending intent or touching the tablet.

#### Scenario: Exact historical request recovery
- **WHEN** an explicitly supplied original PendingIntentRequest matches a validated historical publication
- **THEN** recovery SHALL return only its original historical acknowledgment/provenance, even if current SDK acquisition is unsupported, and SHALL NOT allocate new IDs, mint ReaderContext or replay an effect.

#### Scenario: Invalid selected startup metadata
- **WHEN** generic storage accepts a selected snapshot but strict conversation schema or chronology validation fails, or the opened Store contains unavailable commits
- **THEN** startup SHALL report unavailable without adapter-capability data, under the existing shared admission and cumulative read allowance.

#### Scenario: Availability before an active request
- **WHEN** startup needs to report the selected refusing transport's availability before a Reader request exists
- **THEN** it SHALL inspect typed availability without invoking acquisition or interpreting a request-guard failure as unsupported capture, and actual request acquisition SHALL retain its guards.

#### Scenario: Persisted mode before runtime construction
- **WHEN** an existing Store has an explicit nonlocal or contradictory publisher mode
- **THEN** startup SHALL validate the actual mode before credentials/model/device construction and refuse an unsupported or mismatched runtime without ordinary all-history fallback; unconfigured compatibility and local-only data access SHALL remain distinct from shared authority.
- **AND** with no `reader.selection`, the actual CLI SHALL exit unsuccessfully with empty stdout and a fixed private-data-free diagnostic while retaining early preflight/no-write checks; successful fixed JSON responses remain scoped to selected-config startup and explicit report commands.

#### Scenario: Configured shared receiving lifetime
- **WHEN** a current selected history report consumes data in configured shared mode
- **THEN** it SHALL retain the matched existing shared-mode lease alongside actual domain/Store admission through consumption, without granting provider/root/native permission or treating local data leases as mode guards.
