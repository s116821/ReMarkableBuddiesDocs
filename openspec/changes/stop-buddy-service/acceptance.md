# Acceptance and enablement evidence

acceptance-cases.json is a closed checklist of concrete variations and required
outcomes for implementation fixtures. These are NOT executed product tests.
Synthetic accepted tuples exist only inside isolated fixtures; they never enroll
observed tablet bytes or enable a production profile.

After independent precode acceptance, implement the vectors through the real
private parser/sampler and host controller, then both actual factories and shared
browser/Electron UI. Exercise all action/state/current/reference/connection/boot
cross-products, not only examples. Enumerate actual maintenance peers from final
admitted source (currently19 predecessors), both Busy directions, observation
quiescence, queued late reply/Stop/120s expiry, original cancellation and the
2/8/12/13/14-second ceilings. Use actual local POSIX SSH/process/systemctl fixtures
with empty stdin, fixed arguments, stdout/stderr flooding and child cleanup.
Run final Linux/Windows source and retained-package integration; distinguish
source resource revisions and package hashes. Never relabel a synthetic pass as
physical shutdown qualification.

Production ordinary-manual enablement requires independently accepted immutable
source/build provenance, exact deployed unit and effective policies/platform,
and actual idle/active interruption across every mode that binary can run.
Evidence must establish application/native effects, flush/durability limits,
owned-child/cgroup retirement, configured signal/escalation and timeout behavior,
and a truthful supported recovery/handback procedure after failure. Ordinary
source currently supplies no established all-mode shutdown proof or binary binding.

Production resident-installed enablement additionally requires the exact installed
Profile/LeaseRecord/artifact/policy tuple and owner-qualified active Reader/Writer
cancellation, terminal Buddy/group retirement, helper success/failure/watchdog
paths and independent stock identity/readiness. Preserve occupied latch semantics
through all cases. Source delivery and actual supported tablet model/firmware/kernel
must match the accepted tuple. Newer unmerged RM2 notebook reuse evidence does not
satisfy those requirements or establish RM1 compatibility.

For each profile, Maintainers and native owners must identify the exact evidence and release
that satisfy these gates before code admits that tuple. No per-device flag or
self-reported readiness can substitute. Unsupported production remains a refusal;
independent contract/transport/UI fixture work can proceed after review. Keep the
paired change active through actual implementation, qualification, spec sync and
archive; no planning-only release or claim of completed Stop functionality.
