## Preferred proposal: separate typed observations
Namespace UnassociatedFeedback, serialized unassociated-feedback; domain schema1, envelope version1, no media. A record has a schema, deterministic record identity, origin actor, original operation, typed kind/reason and caller-owned observation timestamp. Retention derives actor from Store, validates non-nil operation and exact serialization bounds, and accepts no raw message, provider/auth/request/answer text or conversation/turn/page fields. Error and reconciliation descriptions share the existing private static catalog; do not fabricate OutcomeFact identities to reuse it. Unassociated observations cannot certify Completed or Canceled, undo, billing, native output or current operation state.

Use deterministic actor/operation-scoped record, revision and publication-operation identities, separated from the caller operation namespace. Equal literal callbacks return the same retained observation; contradictory content for the same identity refuses. The existing Store mutex/parent/operation checks must enforce this atomically, including the namespace capacity bound. No automatic expiry or deletion. A bounded explicit current-head snapshot/query returns historical descriptions, not a queue of known-undisplayed items; conflicts, tombstones, unsupported/malformed/foreign identities or incomplete Store refuse without partial results. The limit is at most MAX_ITEMS and existing metadata/result bounds; capacity failure must never be reported as retention success. Read/refusal privacy and write-stage residue must be distinguished: generic failed publication can leave accounted immutable objects without a committed observation.

## Adoption and custody proof
No upgrade is performed by ordinary Store::open. The only adoption route is a fresh-open preparation factory that owns a unique Store value, obtains the existing lifetime lease, verifies complete ordinary local state, and activates the feature before exposing Arc/worker handles. It does not mutate an already-shared Store. An already-open old service/store makes lease acquisition busy; the factory must not stop it or navigate the tablet. Service coordination belongs to an independently admitted owner.

The feature marker is actor/generation bound. Publish/sync marker bytes first, publish format3 before any new namespace record can commit, verify exact readback, then expose the prepared facade. Generic publish/import/recovery paths must enforce the new namespace/format/feature relationship, not rely solely on the public wrapper. Existing selected-feature2 bytes and semantics remain distinct: adding feedback does not grant selected/native authority, and selected preparation must never downgrade3 to2.

The exclusive lease is an open-time fence, not a per-publish compatibility recheck. Demonstrate which old entry points cannot obtain a mutable Store after3 and which maintenance paths explicitly refuse3. Current-format-compatible generic operations on the new Store are not all globally disabled. Previously captured metadata values are not new native authority; the usual fresh mode/generation/head checks remain. Cover same-root already-open/in-flight handles, constructor escape/alias prevention, and no live-Arc adoption. Do not assert that a passive historical token or parsing failure fences every possible old writer.

Crash boundaries must be measured: before/after feature marker, before/after format3, before first commit, after immutable-object staging, and after commit before return. No record may be committed under1/2. An interrupted marker alone is not activation. A verified literal committed result can be recognized after an ambiguous return; absent/changed readback remains uncertain/refused, without blind retries or native action. No guessed waits prove success.

## Versioning, recovery and bounded additive restore
Keep contract-v1.json byte-identical. The proposed contract2 and exact feature/capability/report examples are pinned in [reference-vectors.json](reference-vectors.json); they are proposed wire data, not executed Store evidence. Existing legacy1/2 behavior remains unchanged.

Current Store::restore accepts backup1 only, refuses selected history/current selected mode, and merges current manifests plus archive manifests into a staged generation. It is additive, not history replacement. Keep that API and its existing legacy eligibility; add an explicit refusal for activated3 so it cannot invoke the old format1 creator and downgrade. Do not silently make existing ordinary_restore/selected export/restore understand3.

A separate prepared-feedback additive restore route is proposed, only with current3, a valid local feature, complete ordinary current history and no selected feature marker. It accepts archive1 with no new namespace or selected metadata, or archive3 with required feedback_history metadata, no selected metadata and origin_actor equal to the current Store actor. The archive3 new-domain envelopes/payload actors must match that validated origin. Cross-owner archive3 is unsupported in this increment, before staging/effects; do not rewrite original actor/operation/record/revision identities. Legacy archive1 records keep their existing ordinary origin semantics and bytes; they cannot smuggle a new-domain record. Query refuses foreign new-domain identities. The required archive3 metadata prevents an old deny-unknown Backup reader from accepting it as legacy.

The new route preserves the existing additive manifest union/collision semantics and exact original record/media bytes, with capacity/identity checks over the merged result. Stage marker then format3 before copying any new-domain commit, rebuild and validate the union, then atomically publish CURRENT. Preserve the old current generation on preactivation failure; postactivation ambiguity uses readback, not a blind retry. Restoring archive1 into activated3 yields another3, never1. A new generation receives a locally bound structural marker; this does not rewrite original records or confer native authority.

Eligibility is explicit in reference-vectors.json: selected backup2 is inspectable as before but is not restorable by either the existing ordinary route or the new feedback route. Current2, or current3 carrying selection-feature.json, is not eligible for the new additive route. Existing selected2 bytes can coexist and remain historical/queryable under qualified existing selection operations; that is not selected restore permission. New format3 backup export is likewise limited to ordinary3 without selected metadata. Default backup1/selected2 APIs keep their existing behavior and explicitly refuse unsupported3. No installer rollback, safe downgrade or selected restore expansion is provided.

## Generation and capability monotonicity
The existing create_generation helper writes1; its callers are Store::open (fresh bootstrap), storage/recovery.rs (restore) and storage/migration.rs. The proposed preparation path must choose a typed legacy1 or prepared-feedback3 creation policy explicitly. Legacy bootstrap stays1; activated restore stages3 under the retained lease. Generic migrations from or to3 are unsupported until separately registered/qualified, refusing before staging; include migration.rs only for this guard. A registered unrelated migration cannot manufacture feedback activation. There is no supported CURRENT transition from activated3 to1/2; every admitted generation writer must retain3 or refuse. Manual external rewrites and arbitrary old native tools are not fenced by this source contract.

Recover/import must validate the target feature/format before interpreting or committing new-domain manifests, including staged recovery before CURRENT publication. Generic admission cannot bypass the facade. New-domain data under1/2, missing/foreign feature, unsupported target or an interrupted marker refuses complete recovery/publication rather than becoming a usable empty Store. All new namespace/head/capacity checks remain under existing custody.

Store::open currently republishes contract1 and five-namespace capabilities on every successful open. A compatible opener may preserve/rewrite contract1 with identical bytes, but for activated3 must also publish contract2 and capabilities2 with store_versions[1,2,3], six namespaces and the feedback feature declaration; it must never overwrite them with a five-domain capability claim. Validate/read back these declarations before returning a prepared facade. For unchanged legacy1/2 use the existing capability shape/bytes. Capabilities describe supported storage only, never runtime activation; a stale/missing/contradictory publication cannot authorize a downgrade or new namespace write.

Old readers/writers, archive readers, rollback and native behavior remain separate qualifications. Existing maintenance supporting only1/2 stays explicitly unsupported for3; no cache cleanup widening. New namespace live sync is unsupported: both configuration and direct policy requests refuse before network/publication. Production activation and runtime/presentation wiring remain outside this increment. Selected2 coexistence and five-domain regression evidence are still required.
