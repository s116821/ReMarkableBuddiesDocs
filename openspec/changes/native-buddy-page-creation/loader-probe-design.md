# Loader review and read-only discovery probe design

September 26, 2026. Proposal for independent review, not an executable handoff or permission to load. No probe has been implemented, built or run. No device access occurred in this research pass.

## Candidate and compatibility evidence

XOVI is the leading maintained-source candidate, not yet a qualified compatible loader. The upstream [v0.3.3 release](https://github.com/asivery/xovi/releases/tag/v0.3.3) was published March 29, 2026 and exposes ARM32 and AArch64 assets. The [extension bundle v19-23052026](https://github.com/asivery/rm-xovi-extensions/releases/tag/v19-23052026), published May 23, 2026, identifies ARM32 for RM1/RM2. Current upstream commit queries also match the inspected source pins: XOVI June 20, 2026 and extensions September 8, 2026. Release/source activity is maintenance evidence, not a firmware support claim.

The public ARM32 bundle was downloaded to the host only. SHA-256 `9aa00537ad41e9be0c3151992bfc25106465318cf5bb4c41cf59b3ddd4866377` matches its GitHub asset digest. Its xovi.so is 123,620 bytes, SHA-256 `2878d88da2dcb37dcf5533fa78aeeb5cc933eb8c7e5b9041213a4e135a7fff14`, ELF32 ARM EABI5 hard-float, DT_NEEDED libc.so.6, requiring GLIBC_2.4 and GLIBC_2.34. This matches the exported executable's architecture class; actual provider symbols and complete probe dependencies remain a preflight gate. The standalone v0.3.3 ARM32 asset has the same loader SHA-256. The exported xochitl itself requires GLIBC_2.34 and newer versions up to GLIBC_2.38, supporting plausibility of the loader requirement without proving every imported provider symbol. No downloaded binary was executed.

Inspect pinned [XOVI source](https://github.com/asivery/xovi/tree/2b99649f5e4fd6288be7792a8570bd16418adb70) and [extension source](https://github.com/asivery/rm-xovi-extensions/tree/6c709dd8416ddf89034831073d76fb4ee3372905). The bundle build workflow fetches a floating latest loader and toolchain; a tag alone does not establish a reproducible source-to-binary pair. Pin all inputs or retain exact verified asset hashes. ARM32 is explicitly less tested upstream; hooks have race/blocking-lock caveats. Initial discovery should require zero XOVI overrides/trampolines and no broker, resource rebuilder, command executor, UI mod or librarian extension. This avoids those hook paths, but does not prove loader safety.

Build against a verified ARM hard-float sysroot providing compatible Qt Core/Gui/Qml public APIs; do not copy desktop Qt libraries to the tablet. Verify all ELF imports, symbol versions, C++ runtime requirements and Qt feature availability against coordinator-provided provider metadata before loading. Private xochitl class headers, layouts, offsets and C++ entry::Id marshalling are unnecessary for metadata discovery. Qt filename 6.10.3 alone is insufficient. Loader or probe mismatch means stop, not firmware/runtime replacement.

## Exact launcher and rollback limits

The bundle's [start](https://github.com/asivery/rm-xovi-extensions/blob/6c709dd8416ddf89034831073d76fb4ee3372905/xovi-setup/start) executes pre-start scripts, iterates every service directory, unmounts each existing drop-in target, mounts tmpfs over it, copies overrides, writes LD_PRELOAD and XOVI_ROOT, reloads systemd, restarts every listed service, then executes post-start scripts. Its default resource-rebuilder override disables QML disk cache and enables QML file reads/writes. The script does not fail fast on every failed operation. It is not a passive discovery command or a reviewed ready-to-run procedure.

The [stock](https://github.com/asivery/rm-xovi-extensions/blob/6c709dd8416ddf89034831073d76fb4ee3372905/xovi-setup/stock) path runs hooks, unmounts the drop-in directories, reloads systemd and restarts services. Upstream also describes reboot as stock recovery. Neither removes copied files under /home/root/xovi; neither guarantees recovery when unmount/reload/restart fails. Removing an extension file does not unload code already resident in xochitl. Do not use dlclose for probe cleanup.

Before any coordinator dispatch, prepare an exact minimal staging manifest, hashes, service/drop-in/mount baseline, and a coordinator-reviewed command sequence limited to xochitl. Refuse pre-existing or unexpected target mounts/overrides rather than unmounting them. Include no pre/post scripts, resource-rebuilder settings or unrelated services. The startup and rollback service restarts are explicit experimental actions, not per-answer behavior and not currently authorized by this proposal. No persistent boot activation.

Rollback must first remove only the recorded experiment-owned runtime injection, then reload and restart stock xochitl once under coordinator control. Verify executable hash, absence of probe/loader in process maps, expected effective drop-ins, stable PID/start time and NRestarts, and visually restored stock UI. If removal/unmount fails, do not restart with injection still effective. A documented coordinator-controlled reboot is the next recovery option, with post-boot verification; do not reboot automatically. Retain fixture backups and private logs. Claim rollback success only after these checks, not from stock's exit code.

## Concrete first probe: metadata only

The first probe has no inbound command channel. Build-time constants fix the protocol version, expected xochitl fingerprint, allowed classes, output limit and expiry. Coordinator checks the executable hash immediately before activation; the module additionally checks process executable identity before registering discovery. A mismatch produces a terminal refusal. All state is process-local and inert after one attempt.

Register Qt startup handling only from accepted `_xovi_construct`, after XOVI loading conditions and import resolution have completed, and only before a QCoreApplication exists. Late loading is a terminal inert refusal. Do not use static Q_COREAPP_STARTUP_FUNCTION registration in the deployable probe: dlopen executes static constructors before XOVI can reject/unload the module. The candidate explicit registration call is qAddPreRoutine, declared in the public QtCore header and used by that macro; its exact target symbol and behavior still require ABI verification. The callback performs fixed state setup and schedules one context-bound timer/queued callback; GUI inspection starts after event-loop entry. No constructor-time executable hash, dependency scan or metadata traversal. No function interception, blocking queued call, processEvents loop or worker-thread metadata access.

Tagged XOVI v0.3.3 source `0c8d5269b55c851901d4e4a754dc2d7deab40b17` has the same dynamiclinker.c/main.c as the inspected current pin. The complete source search finds one dlclose site, in unloadPass1Result, called only on failed loading conditions in pass 2a; `_xovi_construct` follows passes 2a/2b/2c. A false `_xovi_shouldLoad` returns early without calling construct or dlclose. No later unload API/path was found in this pinned source. This supports a narrowly scoped residency assumption only for the exact reviewed loader and minimal extension set; source audit is not a binary/runtime proof. Fatal later initialization failures may terminate the process and require coordinator recovery. Accepted registered modules stay resident until process exit; no dlclose-based cleanup. Before acceptance, synthetic tests must cover both shouldLoad refusal without registration and failed-condition unload before registration, plus late-load refusal and accepted single-lifetime behavior. The earlier static-registration fixture remains only no-unload host evidence.

A single owner-thread callback scans existing application/window/engine QObject relationships with bounds: at most 512 objects, depth 12, a 20-ms cooperative budget, and at most 32 matching objects. Only same-thread reachable objects are inspected; other-thread boundaries are reported and skipped. QPointer/context lifetime protects deferred callbacks. No reentrant event processing. Do not instantiate QQmlComponent, import modules, create singletons, run JavaScript or evaluate QML to force discovery. Existing windows' qmlEngine relationships may be used after same-thread checks. If dependency-injected controllers are not reachable, report not_observed, not absent or unsupported firmware.

Allowlisted classes are DocumentController, TaskTracker, Library and DocumentLockManager (including the exact namespaces in host-inspection.md). Read class/superclass names and declared method/property metadata only. Report owner-thread equality as a boolean, not process addresses. The first probe does not invoke any native method or arbitrary property getter. isReady/isRunningTasks and document/page values require a subsequent separately reviewed accessor stage after getter side effects and identity mapping are established. Metadata may expose property names/types for that stage; missing identity values remain unknown. No content, titles, strokes, text, account details or complete QObject dumps.

Output is one bounded protocol record (maximum 8 KiB) containing probe build/hash identifier, coordinator correlation nonce, PID/start identity, runtime Qt version, expected executable fingerprint assertion, bootstrap outcome, elapsed time, objects examined, limit/truncation flags and allowlisted metadata. Proposed transport is a single AF_UNIX datagram, sent with a CLOEXEC nonblocking socket and MSG_DONTWAIT to a build-time fixed experiment endpoint under a coordinator-created root-owned mode-0700 runtime directory. The root-owned collector binds a mode-0600 socket before activation, enables credential reception, validates sender PID/UID against the new process and checks the one-use nonce; it writes the private host evidence after collection. Verify directory/socket type, ownership and no symlink traversal before sending. Bound the JSON to 8 KiB before send; truncate complete metadata entries with an explicit flag, never emit malformed partial JSON. Close the sender socket after the one send. No acknowledgement, receive path, retry, network listener, shared broker FIFO, shell execution or synchronous GUI-thread logging. Missing/stale endpoint, failed validation, EAGAIN or send failure means no result. Collector/endpoint cleanup is coordinator-owned and limited to the recorded experiment directory. Exact collector and socket code still require review and synthetic backpressure/credential tests before dispatch.

The queued callback checks a monotonic expiry before scanning, and each loop checks budget. A late callback becomes inert. Host deadline is 10 seconds after the coordinator observes the new process; no response is timeout, not native absence. A cooperative 20-ms budget cannot preempt a stalled Qt call; host timeout cannot safely unwind it. An unresponsive UI/process triggers coordinator rollback, not thread termination or extension unload. No automatic reactivation.

## Host acceptance and review decision

Before device consideration, a synthetic Qt harness must exercise normal startup, delayed/no event loop, pre-expired work, object deletion, wrong thread, limit overflow, oversized metadata, output backpressure and fingerprint mismatch. Inspect the built extension for zero overrides, no command exports, no native method invocation and the exact dependency manifest. These tests prove probe controls only, not tablet behavior.

Independent review should decide whether this restricted existing-object metadata pass has sufficient value despite likely incomplete QObject reachability; whether startup/transport implementation is safe; and whether the exact coordinator activation/rollback procedure and ABI evidence are sufficient. Unresolved transport, provider ABI or bootstrap behavior blocks device dispatch. An import-based singleton resolver would be a different experiment with potential constructor side effects, not an automatic fallback. Page creation, durable receipts, PDF mapping and the final product loader lifecycle remain unqualified.
